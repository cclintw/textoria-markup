# Textoria Markup

Keep one authoritative `corpus.json` for each text. Preserve original paragraph text and stable document, division, paragraph, entity and annotation IDs. The static HTML is a derived view, never an independent editable master. Read [file contracts](references/file-contracts.md) for storage and [workflow](references/workflow.md) for operations.

## 任務目標與完成規則

本 skill 的任務是完成帶有實體命名標註、左側實體分類與清單的前端閱讀頁面，支援透過對話新增、刪除、修改標註，並同步更新頁面及正式詞表。除非使用者明確要求「只清理文本」「只確認結構」「先做到某一步」等階段限制，啟動標註任務即預設執行完整流程；文本準備、結構確認及詞表匯入都是中間步驟，不是交付終點。

使用者說「實體命名」並指定「參考這份 CSV／詞表」，即授權將該參考表套用到指定文本全文，無須另外說「標註」或「建立左側欄」。文本、詞表、範圍與確認可由同一對話先後提供，必須延續，不得因跨回合而重新判斷是否要完成標註。

確認只用來補足必要資訊。已有標註參考表或規則，且文本結構已確認後，必須接續完成：匯入參考資料 → 套用標註 → 重建含左側實體分類與清單的閱讀頁 → 更新 `exports/entity.json`、`entity.csv` → 檢查並交付閱讀連結。使用者對結構預覽回答「是」「繼續」「照做」，即確認該預覽；儲存結果一致時，展示實際結構後直接繼續，不再詢問是否套用詞表或是否繼續。僅在必要資訊缺失、結果與已確認結構有實質差異、執行權限受阻或實際錯誤使流程無法繼續時，才暫停並說明具體原因；解除後接續原任務。

交付前核對詞表已匯入、匹配結果已儲存、左側清單與正文標註來自最新資料、正式詞表已更新。僅建立結構或未標註閱讀頁不能宣稱任務完成；若沒有匹配，明確報告零匹配原因，不得捏造標註。後續對話修改也須完成儲存、重建與檢查。完整流程不自動包含另行發布網站、額外匯出格式或未經選擇的 AI 提取。

## User-facing guidance

Address the person using the skill: report the result, show review links and ask only the next necessary question. Do not include implementation changes, test counts, internal hashes or development narration unless requested. A `faq:` prefix in this project's dialogue denotes normal end-user operation, not a request to explain the implementation.

After every structure creation or revision, provide the actual resulting chapter hierarchy for review, including when the user supplied the TOC. For a long hierarchy, generate a disposable Markdown TOC preview from the saved corpus and link it, rather than showing only chapter counts or assuming that the supplied TOC substitutes for reviewing the result. Read-only previews do not change the saved structure. Compare the saved hierarchy with the confirmed preview: if they agree, retain that confirmation and continue annotation without another approval; if they materially differ, obtain confirmation of the changed structure first. Further structural edits require a fresh preview.

## Paths and scope

Resolve `<SKILL_DIR>` from this installed skill; `<PROJECT>` is the user's working project. Scripts are under `<SKILL_DIR>/scripts`. All persistent user data belongs under `<PROJECT>/textoria-markup/collections/collection-<ASCII-slug>/`: `uploads/`, editable UTF-8 `clean/<stem>_clean.md` and its preparation report, `corpus.json` after structure confirmation, generated `site/`, derived `exports/`, plus optional hidden `.history/` snapshots. Installation alone creates no user data. Only the original upload and reviewable Markdown preparation are retained before structure confirmation; other preprocessing lives in a system temporary directory, not permanent intermediate/config/candidate files.

Use [runtime](references/runtime.md) before execution. Reuse an available verified Python 3.10+ with the declared dependencies. Never write machine-specific interpreter paths into released instructions. Automatically inspect every uploaded text source or vocabulary/rule text file before parsing or cleaning: strictly validate UTF-8 and check BOMs/readability. If another encoding is reliably identified, decode strictly and use UTF-8 working/output copies without asking for routine conversion; keep original bytes unchanged. Encoding conversion must not normalize characters, punctuation or spelling. Never use replacement/ignore decoding or guess silently when identification is uncertain; report unreadable or ambiguous input before applying it. Binary attachments require their format-specific readers, not UTF-8 conversion. This read-only inspection may precede collection selection; persistent writes still require a resolved collection. New source inputs require encoding/readability inspection; multiple sources require an explicit ordering decision before merging. Body-source formats are TXT, MD, HTML/HTM, and CSV with a named text column. Other attachment formats may be interpreted with appropriate tools, but don't claim unreadable files were normalized.

## New text and external annotation

**主動查詢 Local NER MCP Server 詞表。** 收到文本標註要求且使用者尚未選定標註來源時，先檢查目前 Codex App 是否提供 Local NER MCP Server，即使使用者未指名伺服器也適用。若工具可用，呼叫 `list_reference_sets`。有可用詞表時，在詢問標註來源的同一則訊息中列出名稱與 ID，詢問要採用哪些詞表，並保留下方的其他選項。工具不可用或清單為空時，直接提供下方的其他選項。只有一份參照表、參照表與文本或文集同名，或既有文集曾使用某份詞表，仍須取得使用者的選擇。使用者已明確指定且可唯一辨識的詞表可直接使用。文集歸屬也未指定時，一併詢問。

**標註來源確認。** 開始標註前，須有使用者提供或選定的實體詞表、關鍵詞清單或標註規則。使用者明確選擇 AI 提取時，由指定的提取技能先產生參考詞表，再由 Textoria Markup 套用。Textoria Markup 不自行從正文提取或逐段標註實體。等待使用者選定來源期間，僅進行唯讀查詢。

1. Resolve collection ownership **before writing uploads, cleaned exports, corpus or site**, including cleaning-only requests. Run the read-only `textoria_intake.py` to list existing collections. If the user has not already specified ownership, ask whether this is a new collection or an additional text in a named existing collection; do not infer a new collection from the filename. Reuse an explicit prior answer without asking again. Resolve the choice with `--mode new|existing --collection-slug ...`; the planner creates nothing. After ownership is resolved, immediately archive a byte-for-byte copy under uploads/ (never move the external original) using `textoria_prepare.py`; it also prepares the Markdown working copy without corpus/site. Read the workflow reference for stage boundaries and the current append limitation.
2. Default to the full annotation workflow; stop at a preparation stage only when the user explicitly limits the task to that stage. Inspect encoding and actual cleanup issues; an absent cleaning record is not evidence that cleaning is needed. Ask about consequential cleanup before applying it, preserving Markdown syntax and notes. Always save the prepared text as `clean/<stem>_clean.md` in UTF-8, regardless of supported input format (including HTML/CSV after extraction). Even when no cleanup is needed, save a preserved working copy and record that fact. Explicit cleaning-only requests end with uploads/ and clean/, without structure, corpus or site. Never overwrite an edited working copy. Provide a clickable link to the clean Markdown with its literal # / ## / ### heading markers preserved, supporting full-text reading and heading edits. Do not automatically open it in a panel or browser; let the user choose the link unless they explicitly ask you to open it. For full preparation, read the latest clean Markdown, show proposed division headings/order and paragraph segmentation examples and obtain confirmation before saving structure. Explain that users can edit headings (`# 卷一`, `## 城內`, `### 永寧寺`; space after #) or describe the structure in dialogue. Re-read the working copy after any edits, re-preview changes, and use its SHA-256 to bind the confirmed preview to the build. After confirmation use `textoria_build.py` with the original source plus `--prepared-md <clean.md> --prepared-sha256 <reviewed hash> --no-clean`; corpus is first created at this stage. The legacy combined builder is available for explicitly confirmed automated workflows; do not use it to bypass working-copy review. Existing texts must not be rebuilt from raw source just to change annotations.
3. Ask once for annotation sources when missing. Present these user-facing combinable choices in Traditional Chinese:
   1. **上傳實體詞表或關鍵詞清單**。
   2. **直接描述標註規則**，例如：「將『名曰』之後、逗號之前的二至六字標為人物。」
   3. **由 AI 自動提取實體詞表作為標註參考表**。
   三項選擇須完整呈現，保留原有意思與可複選性；不得把第三項改寫為只提取部分類型，也不得附加帶有未經要求之類型限制的示範回答。使用者選擇 AI 提取而未限定類型時，採提取技能支援的全部適用類型與其原有排除規則，不預設為人物、地名、官職三類。需要一句式回答範例時，僅用「建立新文集，由 AI 自動提取實體詞表」，不要替使用者加入類型清單。若前文由 Agent 自行加入類型限制，而使用者僅沿用該範例或回答「是／繼續」，不得據此把原本未限縮的要求視為已限縮；應先指出該限制並釐清。使用者自行明確指定的類型限制則須遵守，無須重問。此預設僅適用已選擇 AI 提取的任務，不擴張外部詞表／規則的範圍，也不授權未選擇的 AI 提取。交接提取與套用前，依 [optional extractor 的範圍核對](references/optional-extractor.md#scope-check) 檢查類型範圍。
   Keep dependency names and installation mechanics out of this choice list. When option 3 is selected, discover/reuse the extractor or install the configured skill in the background, following required runtime permissions and installer activation instructions; do not ask users to install manually or select the same option again. Perform extraction as soon as the installed skill is available. Users can choose 1, 2, 3 or any combination. **Markup itself must not perform a second AI extraction pass.** Only when the user explicitly selects/requests AI extraction, discover the extractor skill and follow [optional extractor](references/optional-extractor.md) to reuse or install it. Never install or extract merely because a source is missing. Combine newly supplied tables, rules and requested extractor results into one normalized batch before applying, preserving source provenance and conflicts; the existing formal vocabulary and corrections keep priority.
4. Read supplied attachments. Straightforward name/type/alias CSV is supported directly; one-column keywords use `--keywords` and default type `key-word`. For prose, mixed tables, clipper descriptions or unfamiliar columns, Codex interprets them into the normalized JSON in the workflow reference. Use a temporary normalized JSON, with the original passed as `source` and `--normalized` pointing at the normalized file. Do not ask users to write Python or rename their files. No arbitrary uploaded Python is executed.
5. **標註前整理工作詞表。** 用暫存 JSON 或 CSV 整理實體、別名、關係與規則四張表。先核對別名和正名是否跨實體 ID，再用來源明載的同一關係與原文語境確認聚合。已確認同一實體的名稱共用標準名及實體 ID，確定是不同實體的同名項目保留各自 ID，以章節、段落或規則分流。相連的稱呼指同一人且構成一個完整稱謂時，用完整範圍標一處。證據不足者保留候選，正文用虛線底線，右欄顯示候選、類型和段落，待核對項目不列入任何實體的確定次數。既有人工修訂優先，只有會影響結果的歧義才詢問使用者。
6. Resolve action and scope from the user's existing instructions, including the full-workflow authorization above. When the reference input is supplied and structure confirmed, proceed to `apply --confirmed` without another confirmation question. Ask only for missing or ambiguous scope, not authorization already given; never manufacture confirmation. `apply` directly marks matches and persists reusable rules and receipts in corpus, then rebuilds the reader and exports. Same-span type/identity conflicts stay visible; partial overlaps remain reported in `annotation_state.overlaps`, not silently discarded or represented as successfully applied.
7. Complete and inspect the annotated reader, including its left entity categories/list and body highlights, and report completion/errors honestly with a reading link. Update `exports/entity.json` and `entity.csv`; keywords are included using `key-word`. An unannotated structure build is only an intermediate result unless explicitly requested as the stopping point. No automatic SNA, co-occurrence graph, translation or semantic extraction. Counts are derived for the reader, not a separate analysis pipeline.

**專用參照表。** 標註完成後，JSON 匯出實體、別名、關係及規則，CSV 匯出標準名、類型、別名、來源和座標。逐處標註、位置索引及字元位移留在 `corpus.json`。重新標註時驗證新結果後替換網站與同名匯出檔。

**本機網站交付。** 產生閱讀網站後，用僅監聽本機的 HTTP 靜態伺服器提供文集的 `site/` 目錄，在 Codex 瀏覽器直接開啟 `read.html`，並交付可點擊的 localhost 網址。確認頁面可讀，有地名座標時也確認右欄地圖可開啟。地名來源的顯示規則見 [閱讀頁資料規格](references/file-contracts.md)。

## Review and dialogue correction

The reader's existing UI is the shared theme. Users inspect the original and KWIC, copy a selected occurrence/paragraph/entity, then add an instruction in dialogue. The plus button copies a single unannotated selection, its paragraph ID and Unicode `[start,end)` positions. It does not save or send a message.

**For every add/delete/change, confirm action and scope before mutation.** Copied current-selection data can target one occurrence; paragraph data can target that paragraph or all occurrences; entity data targets shared entity metadata. Do not assume the user wants a global change. For a confirmed conditional bulk cleanup, resolve the exact saved annotation IDs from the current corpus and use one `delete` request with `scope: all` and `annotation_ids: [...]`; this preserves original text, independent keywords and per-occurrence exclusions. Only delete entire annotations when all their types/identities are within the requested cleanup; use selective scoped edits if other types need to remain. Preserve exceptions such as text inside paired 《…》 according to the confirmed condition. Use `textoria_workbench.py plan` to count impacts, then `edit` with the current corpus revision, confirmed scope and `confirmed: true` after authorization. Preserve attributes the user did not ask to change. For a confirmed whole-book entity type change, use `modify-term` with `scope: all`, the original `term_id` and new `markup_id`; it updates the formal term and linked annotations while preserving IDs, aliases, independent keywords and other identity alternatives. Use scoped occurrence edits for partial changes instead. New types are created as part of the confirmed action; ask only if a near-duplicate label is ambiguous.

Edits never change source text. Deletions retain the entity master and record scoped exclusions, preventing reruns from reviving removed tags. Existing saved/manual annotations win over reruns. Corpus writes are atomic and revision-checked; generated site and vocabulary exports publish from staging with rollback on publication failure. If publication fails after a valid corpus save, say the master was saved but the view is stale, and rerun rebuild; do not report the webpage as updated.

After edits, verify and regenerate site/exports, then refresh the local HTTP reader while preserving chapter and selection. The shared reader embeds its data, and the browser never writes directly to the corpus.

Use Traditional Chinese display names for known types and stable English `markup_id` values for matching/export. Known imported slug fallbacks use assets/annotation/type_labels_zh-TW.json. Keep explicit user-supplied display names and never change type IDs or annotation categories merely to translate a label; for unknown English types, determine a suitable Chinese display label from the supplied definition or clarify if ambiguous.

Structure creation and unannotated reader rebuilds must not create exports/. Generate formal entity JSON/CSV after applying annotation inputs or edits, including accepted terms with zero matches, or when the user explicitly requests an export. Shared default type definitions alone do not justify a vocabulary export.

## Identity data

Keep explicit entity/name/mention links in the corpus and derived JSON. Follow [file contracts](references/file-contracts.md#name-identities-and-relational-json-identity-schema-10) when changing identity data or exporting JSON. Preserve existing IDs and scoped corrections. Legacy noncanonical spellings remain unclassified unless supported by evidence; adding a name ID does not confirm an alias or merge entities. HTML displays existing links rather than defining identities.

## Templates, exports and migration

The shared chapter dropdown exposes actual division levels: indent levels 2 and 3 by 16px per step, cap deeper indentation at level 3, and use 18/16/14/12px fonts for levels 1/2/3/4+. Use the shared accessible custom listbox so native platform option styling cannot flatten the hierarchy.

When a selected division has no own paragraphs, the reader keeps its heading and displays the path to its first readable descendant, continuing through multiple empty levels. Preserve the actual paragraph/annotation IDs and owning division for copy/KWIC navigation; never change corpus structure or pull in unrelated sibling content. Divisions with their own text keep their existing single-division view.

Use `themes/default/templates/` with `parts/` for header/footer/sidebar/chapter/body composition; CSS and JS are shared under `static/`. Reader and Help footers contain only “Generated by Textoria Markup”, with the name linked to https://github.com/cclintw/textoria-markup; retain 12px compact styling and omit personal developer credits. The renderer fills templates with corpus data and copies static assets. Corpus-specific KWIC data is generated, never shipped inside the reusable theme. Do not introduce a per-text theme fork for routine content differences.

The three public exports are (1) self-contained reader HTML with both sidebars and hierarchical chapter navigation, (2) CSV/Excel DocuSky metadata tables, and (3) DocuXML. Read [exports](references/exports.md) and use `textoria_export_bundle.py <COLLECTION> --format html|table|docuxml|all` on explicit request. Icons follow + in that order and only copy prompts. Single-file HTML embeds CSS, JS and full book data, removes top add/export/help actions, retains sidebar toggles and in-file KWIC locating. DocuXML defaults to one level-1 division per document, collecting every descendant paragraph once and preserving the full division hierarchy in custom metadata; metadata tables use identical filenames/rows. Resolve optional spreadsheet runtime paths before CSV/Excel export; do not silently install dependencies. For DocuSky, DocuXML is the completed-annotation build file; CSV/Excel is the metadata companion, not a BatchTagging instruction table. Follow DocuXML 1.3: use only PersonName/LocName/Office/Date as built-ins, declare other types with Udef_ and paired custom feature_analysis entries, and check required corpus/filename plus lexical compatibility and content fidelity before publishing. A successful local check does not establish a live database import. Existing TEI outputs are legacy, not DocuXML. Do not offer TEI, EPUB, SQLite or Access in this skill's export menu.

`textoria_migrate.py` copies old `textoria/` collections into `textoria-markup/` and verifies IDs/text/tags. It never deletes the original or overwrites a destination. Keep the original UI/backup until migration and view comparison pass. Skill updates replace code/templates only, never the user's collection folder. Published root data and backups must be excluded from Git.

## ChatGPT / Sites publishing entry

The globe action after DocuXML copies a collection-specific publishing prompt; clicking is never authorization to publish. An explicit submitted publishing request uses the available Sites skill/tools, generates the latest standalone reader and uses it unchanged as the static index. Initial loads and chapter changes collapse every entity category; a deliberate help return can restore its prior reading state. Default new Sites to private, preserve an existing identified Site’s audience and identity on updates, and return the verified deployed URL. Publish only the reading artifact (which includes the full text and annotations), not uploads, clean files, corpus master, history or unrelated files. For published showcase sites use --format html --showcase: retain the local reader’s top action icons as copy-only commands, and export the complete help as a separate page opened in the same tab, using the local guide layout and return-state behavior; never replace it with a modal or iframe. These controls never mutate corpus or grant editing rights. Plain reading-only HTML exports may omit these controls. Publishing is a snapshot, not automatic corpus synchronization. If Sites is unavailable, explain and provide the local standalone reader; do not silently switch hosting platforms.
